# Publishing

Builds run on GitHub Actions and are uploaded over FTPS to shared hosting. There is no build
server to maintain — `.github/workflows/publish.yml` is the whole of it.

Two sites come out of one workflow run:

| Host | What it is | Source |
|---|---|---|
| `repo.drawethree.dev` | Maven repository — `/releases` and `/snapshots` | generated by Maven |
| `ci.drawethree.dev` | Build listing and jar downloads | `ci/index.html` + `builds.json` |

## One-time setup

### 1. DNS

DNS is on Cloudflare. Both records point at the web hosting — the same address the apex uses,
not the game server address the `play` and `demo-*` records use:

```
repo    A    185.129.138.221    DNS only
ci      A    185.129.138.221    DNS only
```

**Both are deliberately DNS only (grey cloud), and should stay that way** unless you go through
the list below. Turning the orange cloud on breaks a Maven repository in two ways that are
invisible from a browser:

- **Browser Integrity Check** and **Bot Fight Mode** reject requests without a browser
  `User-Agent`. Maven sends `Apache-Maven/3.9.x` and Gradle sends its own; both get a 403. The
  site looks perfect to you and resolves for nobody. Bot Fight Mode is zone-wide on the free plan
  and cannot be scoped by a WAF rule, so it has to be off entirely; Browser Integrity Check can
  be skipped per-hostname with a WAF custom rule on `http.host in {"repo.drawethree.dev"
  "ci.drawethree.dev"}`.
- **Caching.** `.jar` is in Cloudflare's default cached-extension list. That part is harmless —
  releases are immutable and snapshots are timestamped — but a cached `maven-metadata.xml` is
  not. The publish workflow reads the live metadata and merges into it, so a stale copy would
  quietly unpublish whatever versions it was missing. You would need a cache rule bypassing
  `maven-metadata.xml` and `/builds.json`, and cache-busting on the workflow's fetches.

The upside of proxying is saved bandwidth on shared hosting. For a jar this small it is not worth
the two failure modes above.

Whatever you do, if you later add an `ftp` record for uploads, leave it **DNS only** —
Cloudflare proxies HTTP/HTTPS only, and FTP through the orange cloud does not work at all.

### 2. Subdomains on the hosting

Hosting is Forpsi. Subdomains are served out of `/subdoms/`, **not** out of a folder in the web
root:

```
/subdoms/repo    ->  repo.drawethree.dev
/subdoms/ci      ->  ci.drawethree.dev
/www             ->  the portfolio site at www.drawethree.dev
```

A folder you create yourself at `/www/repo` is served at `www.drawethree.dev/repo/` and nowhere
else — uploads to it succeed, and the subdomain 404s. Mapping a subdomain in the panel creates
its `/subdoms/` directory, and the mapping takes a few minutes to reach the web server after the
panel reports success.

Until the mapping applies, the name falls through to the catch-all vhost and serves the portfolio
site. **A 200 is not proof the subdomain works** — check the content, or upload a probe file and
fetch it back.

TLS needs nothing. The hosting already serves a wildcard `*.drawethree.dev` certificate (Actalis,
via the Aruba front end), which covers both names. That matters more than it sounds — Maven 3.8.1
and later refuse plain-HTTP repositories outright, so without HTTPS nobody could depend on this
at all.

Verify a subdomain is really live before wiring up anything else:

```bash
curl -sI https://repo.drawethree.dev/ | head -1
curl -s https://repo.drawethree.dev/ | head -c 200   # must NOT be the portfolio page
```

### 3. Repository secrets

`Settings → Secrets and variables → Actions → Secrets`:

| Secret | Value |
|---|---|
| `FTP_HOST` | `ftpx.forpsi.com` — hostname only, no `ftp://` |
| `FTP_USERNAME` | `www.drawethree.dev` (Forpsi uses the domain as the login) |
| `FTP_PASSWORD` | the FTP password |

Explicit FTPS is supported and verified against this host, so `ftp:ssl-force true` in the workflow
holds — the password never crosses the wire in the clear.

The web IP does not answer on port 21 at all; FTP lives on `ftpx.forpsi.com`. There is also an
OpenSSH on port 2222 of the web IP, publickey-only, if a Forpsi plan ever exposes SFTP — that
would be the better transport, since CI would hold a revocable key rather than the account
password.

That is the main hosting account, which reaches the whole site. If Forpsi lets you add an FTP
account scoped to `/subdoms`, use one — and rotate this password if it has ever been pasted
anywhere.

### 4. Repository variables

`Settings → Secrets and variables → Actions → Variables` — only needed if your document roots
are not the defaults:

| Variable | Default |
|---|---|
| `FTP_REPO_PATH` | `/www/repo` |
| `FTP_CI_PATH` | `/www/ci` |

The defaults match the current Forpsi layout, so neither variable is needed unless that changes.
They are paths **as the FTP account sees them** after login — a scoped account may be chrooted
somewhere else, in which case log in once with any client and copy what you see.

## Publishing

**A snapshot** — push to `master`. Deploys `1.0.0-SNAPSHOT` to `/snapshots` and adds a row to
the build listing.

**A release** — tag it:

```bash
git tag v1.0.0
git push origin v1.0.0
```

The tag is the source of truth: the workflow stamps `1.0.0` into the pom before building, so the
artifact and the tag can never disagree. It deploys to `/releases`, publishes a GitHub release
with the jars attached, and marks the build green on the listing page.

Bump the pom to the next `-SNAPSHOT` after releasing (`1.0.1-SNAPSHOT`), so master snapshots stop
colliding with the version you just shipped.

## How it works, and why

FTP has no HTTP `PUT` endpoint, so `mvn deploy` cannot talk to the host directly. Instead:

1. Maven deploys into a local `staging/` directory with `-DaltDeploymentRepository`, producing
   exactly the tree a Nexus would serve.
2. `lftp mirror -R` uploads it.

The one subtlety is `maven-metadata.xml`, which lists every published version. A `file://` deploy
merges into whatever metadata is already at the target — and a fresh staging directory has none,
so it would publish a version list containing exactly one version and silently erase the rest.
The workflow therefore `curl`s the live metadata down into `staging/` first. **If you rework
these steps, keep that seeding step.**

The mirror runs without `--delete`, deliberately. This tree only ever grows; a bad local state
should not be able to unpublish a release someone already depends on.

Runs are serialised through a `concurrency` group. Two publishes at once would race on the
metadata and the loser's version would vanish from the list.

## Troubleshooting

**The upload fails with `530 Login authentication failed`.** Check the FTP allowlist before
touching the password. Forpsi restricts FTP by country under `Webhosting → drawethree.dev → FTP`,
and the account was originally limited to Czech Republic and Slovakia. GitHub's runners are Azure
machines in the United States, so they were refused — and Pure-FTPd returns the same `530` for a
geo-blocked account as for a wrong password, which makes it look exactly like a credential fault.
The IP field is no help: GitHub publishes over 5,000 IPv4 ranges for Actions and rotates them.

United States is now on the allowlist, which is what makes this work. If a run starts failing on
login again, check whether that entry survived, and whether GitHub has moved your job to a region
outside it.

**The smoke test fails with 403.** Hotlink protection or a `mod_security` rule that rejects
requests without a browser `User-Agent`. Maven sends `Apache-Maven/3.9.x`. Reproduce it:

```bash
curl -A "Apache-Maven/3.9.9" -I https://repo.drawethree.dev/releases/
```

If a browser works and that does not, ask your host to disable hotlink protection on the
subdomain.

**The smoke test fails with 404 while the upload reported success.** The upload is going to the
wrong depth. `staging/` starts at the group path, so the mirror target has to carry the
`releases`/`snapshots` segment itself — without it everything publishes one level too high and
Maven never sees it.

**The upload fails on the certificate.** Shared hosts often present a certificate that does not
match the FTP hostname. Set `ssl:verify-certificate false` in both `lftp` steps — you lose
certificate checking but keep the encryption. Do not switch off `ftp:ssl-force`; that sends the
password in cleartext.

**A version is missing from the listing but the jar is there.** The metadata seeding step failed,
probably a 404 while the site was still being set up. Re-run the workflow; it re-reads what is
live and merges again.

**Downloads work but Maven still resolves nothing.** Check `Options +Indexes` is applied and that
`.jar` is served as `application/java-archive` — `hosting/repo.htaccess` handles both, and is
uploaded to the repository root on every run.
